# Nexus

> 一个面向 GitHub Copilot 的多 Agent 开发编排系统。
> 目标是：**把长任务拆小、把复杂问题分层、把研究与实现分开，从而降低上下文负担并提高实现质量。**

## 为什么做这个

单模型在处理长开发任务时，常见问题不是“能力不够”，而是：

- 一次要看太多代码、太多历史、太多需求
- 一边研究一边实现，容易边做边改口径
- 任务过大时，后半段质量明显下降
- 多轮修改后容易偏离原目标
- 明明是确定性实现，也被迫重复消耗高质量推理成本

Nexus 的核心思路很简单：

**复杂任务不要让模型一口气做完。**
先研究清楚，再分层拆解，再把每一步交给实现者完成。

这样可以让 `Generalist` 每次只处理更小、更明确的一段工作，减少一次性承担过多实现内容导致的质量下降。

## 安装

### 1. 安装文件

将 `skills`与 `agents` 文件夹放到以下目录，若不存在请自行创建：

windows 系统：
```windows
%USERPROFILE%\.copilot
```
其他系统请查看 GitHub Copilot 官方文档，找到对应的用户配置目录。

### 2. 配置各 Agent 的使用模型
在每个 agent 的文件头配置中，设置 `model` 字段，例如：

```text
model: [mimo-v2.5-pro (oaicopilot),deepseek-v4-pro (oaicopilot)]
```
github copilot 会按顺序尝试使用列表中的模型，直到成功为止。你可以根据需要调整模型的优先级和组合。

选择的模型都需要在模型管理页面中启用

### 3. 可选：配置第三方模型

GitHub Copilot 可通过插件 **OAI Compatible Provider for Copilot** 配置第三方模型。

## 核心理念

Nexus 不是让多个 Agent “同时乱做事”，而是让它们**按阶段协作**：

- `Nexus` 负责编排任务
- `Investigator` 负责研究和拆解复杂问题
- `Generalist` 负责按确认后的方案直接实现
- `Reviewer` 负责独立检查结果
- `DocWriter` 负责同步文档与事实缓存

对于小任务，可以直接实现。
对于复杂任务，Nexus 会先要求 `Investigator` 做分层研究，把问题拆成更小的实现单元，再让 `Generalist` 逐步完成。

---

## 特性

- **复杂任务自动分层**
  - 先研究，再实现
  - 避免一个模型一次吞下过大的功能范围

- **减少单次实现负担**
  - `Generalist` 不需要反复重做研究
  - 每次只处理当前明确的一步或一个功能块

- **文件化交接**
  - 研究、方案、实现、评审都有落盘产物
  - 不依赖聊天记忆传递关键结论

- **更适合长任务**
  - 支持中断恢复
  - 支持多阶段推进
  - 支持逐步评审与归档

- **更稳定的任务质量**
  - 复杂任务先拆解，再逐步落地
  - 减少因任务过大造成的实现漂移和遗漏

## 工作方式

### 小任务

对于范围清晰、改动很小的问题，Nexus 会尽量走快速流程：

```text
Nexus
  → Generalist
  → Reviewer（按需）
  → 完成
```

### 复杂任务

对于跨模块、需求不够简单、实现量较大的任务，Nexus 会先让 `Investigator` 研究和拆解，再交给 `Generalist` 分步实现：

```text
Nexus
  → Investigator 研究总体方向与架构
  → Investigator 输出方案 / 步骤拆分
  → Generalist 按步骤实现
  → Reviewer 独立验证
  → DocWriter 同步文档与事实
  → 完成
```

### 这样做的意义

**让 `Generalist` 每次实现的内容更少、更聚焦。**

这会直接带来几个好处：

- 降低一次性实现过大功能时的失误率
- 减少模型中途遗忘前文的概率
- 降低“研究、编码、验收混在一起”带来的自洽幻觉
- 提高复杂任务后半程的稳定性

---

## 适用场景

适合：

- 大仓库开发任务
- 跨模块改造
- 长链路功能开发
- 分多步落地的重构任务
- 容易中断、需要恢复的任务
- 需要把 UI 和逻辑分阶段推进的任务

不太适合：

- 几行代码就能完成的小改动
- 无文件系统的纯聊天环境
- 只想单轮拿结果、不关心过程产物的场景

---

## 使用方式

安装完成后，在 Copilot 的模式选择中选中：

`Nexus`

然后直接输入你的任务，例如：

- 修复一个 bug
- 实现一个新功能
- 继续上次未完成任务
- 开始一个复杂重构任务

如果任务比较复杂，Nexus 会先进入研究和拆解阶段，而不是直接让实现 Agent 一口气完成全部内容。

## 目录结构

```text
.Nexus/
  plan.md
  0-fact/
  1-research/
  2-Scheme/
  3-implement/
  4-review/
  .search-cache/
  .tool/
```

### 说明

- `plan.md` - 当前任务状态、阶段和恢复点
- `0-fact/` - 当前代码事实缓存，减少重复读源码
- `1-research/` - 研究文档
- `2-Scheme/` - 已确认方案与步骤拆分文档
- `3-implement/` - 实现记录
- `4-review/` - 评审记录
- `.search-cache/` - 外部检索缓存
- `.tool/` - 辅助脚本

## 设计重点

### 1. 研究和实现分开

复杂任务先研究清楚，再交给实现者执行。
这样可以避免模型在“边理解问题边写代码”的状态下做出不稳定修改。

### 2. 复杂任务先拆小

不是把整个需求一次性塞给 `Generalist`，而是先拆成更小、更明确的实现步骤。
这样每一步都更容易：

- 实现
- 评审
- 回滚
- 继续推进

### 3. 用文件代替记忆

任务中的关键结论会写入文件，而不是依赖长对话记忆。
这让长任务更容易恢复，也更不容易丢信息。

### 4. 让实现者只关注当前一步

`Generalist` 的价值不在于自己重新研究全部代码，而在于基于已确认方案，稳定完成当前实现。
这也是 Nexus 降低复杂任务质量波动的关键。

---

## 典型收益

相比单 Agent 直接做完整长任务，Nexus 更适合在以下方面获得收益：

- **更低的上下文压力**
- **更少的重复研究**
- **更清晰的任务边界**
- **更稳定的复杂功能实现质量**
- **更容易恢复和继续未完成任务**

尤其是在复杂任务里，真正有效的不是“更强的模型”，而是：

**不让模型一次承担过大的实现面。**

- 依赖运行环境支持多 Agent、文件与工具
- 依赖模型基本遵守角色边界
- 如果研究质量不足，下游实现质量也会受影响
- 超小任务可能会感觉流程偏重
- 更适合开发流程，不是通用聊天框架

## 实践案例

### 在大型项目中配合 `mimo-v2.5-pro` 的使用反馈

在大型项目场景下，`Nexus + mimo-v2.5-pro` 的组合表现尤其明显。

相比让单个模型一次性处理大范围需求，Nexus 会先让 `Investigator` 对复杂任务做分层研究和步骤拆解，再把更小、更明确的实现单元交给 `Generalist`。这使得 `mimo-v2.5-pro` 不需要在单次上下文中同时承担过多模块、过多调用链和过多未确认细节。

实际使用中的典型收益包括：

- **代码质量显著提高**
  - 单次实现范围更聚焦，结构更稳定
  - 更少出现“前面改对了、后面又带偏”的情况

- **bug 显著减少**
  - 复杂功能被拆成多个更小步骤后，遗漏边界条件和调用方的概率明显下降
  - 独立评审和文档化交接进一步降低了回归问题

- **更适合大型仓库**
  - 面对跨模块、长链路任务时，不需要让模型一口气吃下全部上下文
  - 更容易在中断后继续推进，也更容易定位问题出在哪一步

这类收益并不主要来自“换了更强的单模型”，而是来自 **先拆解复杂度，再让模型执行更小、更清晰的任务**。  
在这一工作方式下，`mimo-v2.5-pro` 在大型项目中的稳定性和产出质量会更容易发挥出来。

## 文档模板规范

Nexus 不是“文档堆”，而是一个**结构化工作流系统**。每个阶段文档都有固定模板，确保：

- `Investigator` 输出是可预测的
- `Generalist` 读入的信息是固定形状的
- `Reviewer` 可以按模板逐项检查
- `DocWriter` 可以稳定同步，不依赖自由发挥

### 文档类型与用途

| 文档类型 | 路径 | 用途 | 生成角色 | 消费角色 |
|----------|------|------|----------|----------|
| **事实缓存** | `.Nexus/0-fact/` | 代码文件的注释式摘要，避免重复读取源码 | `DocWriter` | 所有 agent |
| **研究文档** | `.Nexus/1-research/` | 架构级方案、功能级预研、UI 设计方案 | `Investigator` / `UI_Investigator` | `Nexus` / 用户 |
| **方案文档** | `.Nexus/2-Scheme/` | 用户确认后的方案、步骤拆分文档 | `DocWriter` | `Generalist` / `UI_Coder` / `Reviewer` |
| **实现文档** | `.Nexus/3-implement/` | 实现情况记录，包含修改文件、新接口、逻辑变更 | `Generalist` / `UI_Coder` | `Reviewer` / `DocWriter` |
| **评审文档** | `.Nexus/4-review/` | 评审结论、证据矩阵、修复要求 | `Reviewer` | `Nexus` / `Generalist` |
| **任务计划** | `.Nexus/plan.md` | 当前任务状态、阶段、恢复点 | `Nexus` | 所有 agent |

### 模板字段说明

#### 事实缓存 (`0-fact/`)
- `@file` — 文件路径、职责、依赖关系
- `@class` — 类的目的、构造函数输入、重要字段、公共方法
- `@function` — 函数目的、输入输出、算法摘要、边界情况
- `@field` — 字段所有者、语义、类型、消费者
- `@flow` — 流程触发条件、步骤、成功/失败结果

#### 实现文档 (`3-implement/`)
- `<!-- NEXUS_HANDOFF -->` — 文档头，包含状态、路径、下一步 agent
- `Contract Inputs` — 任务 ID、目标、范围、方案来源
- `Files Modified` — 修改的文件及目的
- `New Interfaces` — 新增接口的签名、目的、输入输出
- `New External Fields` — 新增字段的语义、类型、消费者
- `Logic Summary` — 主流程、分支逻辑、错误路径
- `Behavior Summary` — 最终行为、与旧行为对比、是否 breaking change

#### 评审文档 (`4-review/`)
- 验收证据矩阵（验收项、证据类型、证据来源、结论）
- 静态审查维度（逻辑正确性、错误处理、边界条件）
- 测试补强记录
- 真实执行命令与结果
- 严重度判定（HIGH / MEDIUM / LOW）
- 通过/不通过门

### 生命周期

```
研究文档 → 用户确认 → 方案文档 → 实现文档 → 评审文档 → 归档
    ↓           ↓           ↓           ↓           ↓
  .old/       落盘        消费        验证        .old/
```

### 校验规则

- 文档必须符合对应模板结构
- 必填字段不得缺失
- 阶段不得跳步
- 前后文档必须一致
- 未完成字段必须标记 `TODO`

## 阶段流转图

```text
┌─────────────┐
│   任务输入   │
└──────┬──────┘
       ↓
┌─────────────┐
│  简单任务？  │
└──────┬──────┘
       ↓
┌──────┴──────┐
│             │
↓             ↓
是            否
│             │
↓             ↓
┌─────────┐  ┌─────────────┐
│ Generalist│  │ Investigator│
│ 直接实现  │  │ 研究与拆解  │
└─────┬─────┘  └──────┬──────┘
      │               ↓
      │        ┌─────────────┐
      │        │ 用户确认方案 │
      │        └──────┬──────┘
      │               ↓
      │        ┌─────────────┐
      │        │ DocWriter    │
      │        │ 落盘方案     │
      │        └──────┬──────┘
      │               ↓
      │        ┌─────────────┐
      │        │ Generalist   │
      │        │ 分步实现     │
      │        └──────┬──────┘
      │               ↓
      │        ┌─────────────┐
      │        │ Reviewer     │
      │        │ 独立评审     │
      │        └──────┬──────┘
      │               ↓
      │        ┌─────────────┐
      │        │ DocWriter    │
      │        │ 同步事实     │
      │        └──────┬──────┘
      │               ↓
      ↓               ↓
┌─────────────────────────┐
│       任务完成           │
│  归档文档 → 合并分支     │
└─────────────────────────┘
```

### 阶段说明

1. **研究阶段** — `Investigator` 分析问题，产出架构级方案
2. **方案确认** — 用户选择并确认方案
3. **方案落盘** — `DocWriter` 将确认方案写入 `.Nexus/2-Scheme/`
4. **实现阶段** — `Generalist` 按方案逐步实现
5. **评审阶段** — `Reviewer` 独立验证实现
6. **事实同步** — `DocWriter` 更新 `.Nexus/0-fact/`
7. **归档阶段** — 文档移动到对应 `.old/` 目录

---

## 约束原则

### 1. 不跳阶段

- 研究未完成，不得进入实现
- 方案未确认，不得开始编码
- 评审未通过，不得归档文档
- 事实未同步，不得提交代码

### 2. 不混合职责

- `Investigator` 只负责研究，不负责实现
- `Generalist` 只负责实现，不负责研究全局
- `Reviewer` 只负责评审，不负责修复业务逻辑
- `DocWriter` 只负责文档，不负责代码

### 3. 不依赖聊天记忆

- 所有关键结论必须写入文件
- 任务状态由 `plan.md` 维护
- 代码事实由 `0-fact/` 缓存
- 方案确认由 `2-Scheme/` 记录

### 4. 不在实现阶段重新研究全局

- `Generalist` 基于已确认方案实现
- 若发现方案有误，应返回 `BLOCKED`，而非自行重新研究
- 实现过程中的局部问题可自行解决，但不得改变全局架构

### 5. UI 必须等逻辑层完成

- UI 实现必须在最后一步
- 上游逻辑接口必须先完成
- 没有确认 UI 方案，不得调用 `UI_Coder`

## 协议驱动的工程系统

Nexus 本质上是**一套围绕文档模板运转的工程协议层**：

- **任务协议** — 定义任务如何拆解、分配、跟踪
- **交接协议** — 定义 agent 之间如何传递信息
- **审阅协议** — 定义如何验证实现质量
- **归档协议** — 定义文档何时、如何归档

这使得 Nexus 不仅是“多 agent 编排”，更是一个**可验证、可恢复、可审计的结构化开发流程框架**。
