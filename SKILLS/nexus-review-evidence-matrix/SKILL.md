---
name: nexus-review-evidence-matrix
description: 该 skill 定义了 `Reviewer` 在评审时必须遵守的证据驱动评审协议，以确保评审基于确认方案、真实代码、真实测试和 fact 一致性，而不是凭印象放行。
---
## 目标
该 skill 用于让 `Reviewer` 以证据驱动方式评审。
核心原则：
- 先理解 fact 上下文
- 再读取确认方案
- 再读取实现报告
- 再查真实代码
- 再审查 fact 是否与真实代码一致
- 再决定是否补测试
- 再真实执行验证
- 最后给出 PASS / FAIL / BLOCKED
注意：
- 本轮实现者刚更新的 `.Nexus/0-fact/` 是 pending fact。
- pending fact 只能作为待验证对象，不能作为实现正确性的独立证据。
- 真实代码、确认方案、真实测试结果才是最终判定依据。
---
## 输入读取顺序
Reviewer 推荐按以下顺序读取：
1. 任务契约
2. `.Nexus/0-fact/`
3. `.Nexus/2-Scheme/`
4. `.Nexus/3-implement/`
5. 上一轮 `.Nexus/4-review/`，若是修复轮
6. 真实源码
7. 测试 / 构建 / 类型检查配置
说明：
- `.Nexus/0-fact/` 可以最先读取，用于建立上下文。
- 但本轮更新的 fact 必须在读取真实代码后再判断是否可信。
- 若 fact 与真实代码冲突，以真实代码为准，并将 fact mismatch 作为评审问题。
---
## 证据优先级
当证据冲突时，按以下优先级判断：
1. 用户确认后的 `.Nexus/2-Scheme/`
2. 真实代码
3. 真实测试执行结果
4. 上一轮 Review 报告，若是修复轮
5. 实现报告
6. 已验证 fact
7. pending fact
8. 研究报告
冲突处理：
- scheme 与实现冲突：以 scheme 为准，除非实现报告给出合理且安全的偏离解释。
- code 与 fact 冲突：以 code 为准，fact 记为错误。
- implementation report 与 code 冲突：以 code 为准，实现报告记为不准确。
- research 与 scheme 冲突：以 scheme 为准。
- test 结果与实现者声称冲突：以真实测试结果为准。
---
## 验收证据矩阵
对每个验收点，都应尽量建立如下矩阵记录：
- 验收项
- 证据类型
  - static
  - automated
  - fact-consistency
  - manual-ui
  - unverified
- 证据来源
  - 源码审查
  - 测试文件
  - 终端命令结果
  - UI 方案文档
  - 实现报告
  - fact 文件
- 当前结论
  - pass
  - fail
  - partial
  - needs-user-review
若关键验收项没有证据，不得默认通过。
---
## 必须核对的输入
### Scheme
核对：
- 目标行为
- Scope / Non-Goals
- 外部接口
- 字段语义
- UI 是否最后一步
- 兼容性要求
- Reviewer Focus
- Done Signal
### Implementation Report
核对：
- 修改文件
- 实现摘要
- 测试命令
- fact 路径
- fact coverage matrix
- 风险
- Doc Impact
- CHANGELOG Candidate
- 是否修复了上一轮问题
### Fact
核对：
- 是否存在
- 是否与代码一致
- 是否覆盖本轮变化
- 是否遗漏关键语义
- 是否错误描述未实现行为
### Code
核对：
- 实际行为
- 边界路径
- 错误路径
- 旧路径清理
- scope 是否越界
- 是否引入无依据兼容层
### Tests
核对：
- 是否覆盖关键风险
- 是否真实运行
- 是否需要补测试
- 测试是否因实现变化同步调整
- 测试是否只是适配错误实现
---
## 静态审查维度
必须检查：
- 逻辑正确性
- 错误处理
- 边界条件
- 结构收口完整性
- 是否遗留旧路径
- 是否引入无依据兼容层
- 是否与确认方案冲突
- 是否误改 scope 外文件
- 是否存在运行时崩溃风险
- 是否存在测试与实现不一致
若是 UI，还必须检查：
- 方案来源是否正确
- 字段 / 状态 / 回调是否与上游一致
- 是否存在明显崩溃点
- 状态覆盖是否完整
- 响应式是否满足方案
- 无障碍是否满足最低要求
---
## fact 一致性检查
Reviewer 必须检查：
- 实现报告是否列出 fact 路径
- 实现报告列出的 fact 文件是否存在
- 修改的主要代码文件是否有对应 fact
- fact 是否与真实代码一致
- fact 是否遗漏本轮外部接口、字段、状态、错误语义变化
- UI fact 是否覆盖状态、响应式、无障碍和旧 UI 清理
若 fact 由本轮实现者刚更新，只能视为 pending fact。
pending fact 必须通过真实代码验证后，才能视为已验证。
---
## 测试补强规则
若现有测试不能覆盖关键风险：
- `Reviewer` 可以新增或修改自动化测试
- 但测试是验证手段，不是代替实现的修复手段
- `Reviewer` 不得借补测试偷偷修业务实现逻辑
- `Reviewer` 不得修改 UI 实现逻辑
---
## 真实执行规则
执行命令必须是真实终端执行：
- typecheck
- lint
- unit test
- targeted test
- build
按项目实际可用命令选择。
禁止：
- 理论上通过
- 未运行却写已通过
- 只看代码就声称测试覆盖了
- 只相信实现者报告中的测试描述而不执行可用验证
若测试环境损坏导致关键验证无法进行，应返回 `BLOCKED`。
---
## UI 专项额外检查
若评审对象包含 UI，必须检查：
- 是否存在确认 UI 方案文档
- 该方案是否来自 `UI_Investigator` 或等价已确认 UI 方案
- 当前 UI 是否确实位于最后收口步骤
- 上游逻辑接口是否已经完成
- UI 所需字段、状态、回调、错误语义是否清晰
- UI fact 是否准确记录状态、布局、响应式、无障碍、旧 UI 清理
若自动化和静态证据足够，但视觉结果仍需人工确认：
- 评审模式应为：
  - `Automated + Manual UI Review Needed`
- 并在评审文档中明确要求 `Nexus` 请求用户手动看效果
---
## 严重度判定
### HIGH
以下情况必须 HIGH，并必须 `FAIL`：
- 明确逻辑错误
- 崩溃风险
- 核心验收失败
- 关键接口 / 字段语义错误
- UI 在无确认方案或无上游接口的前提下被强行实现
- 自动化结果明确失败且影响主目标
- fact 与真实代码行为相反
- fact 描述了未实现行为
- 外部接口或字段变化未写入 fact
- pending fact 误导后续步骤的风险很高
### MEDIUM
以下情况通常 MEDIUM，并通常应 `FAIL`，除非明确无风险：
- 结构不完整
- 遗留兼容层
- 调用方迁移不彻底
- 部分状态覆盖缺失
- UI 流程前置不规范但未立即致命
- 修改主要代码文件但未更新对应 fact
- fact 遗漏关键错误路径或边界条件
- 实现报告与代码有明显不一致但不影响主流程
### LOW
以下情况可 LOW：
- 可维护性问题
- 轻度一致性问题
- 次要命名 / 组织问题
- 不影响主流程但值得修复的瑕疵
- fact 表述略简略但不误导后续判断
---
## 通过 / 不通过门
- 只要存在 HIGH，必须 `FAIL`
- 存在关键验收项无证据，不能轻易 `PASS`
- 若测试环境损坏导致关键验证无法进行，应 `BLOCKED`
- 若只是需要用户看 UI 效果，不是 `FAIL`，但应标记需要手动确认
- 若 fact 与真实代码不一致且会影响后续 agent 判断，必须 `FAIL`
- 若实现文档缺少 fact 更新记录，通常应 `FAIL`
- Review PASS 时，必须归档对应实现文档到 `.Nexus/3-implement/.old/`
- Review PASS 时，不得自动归档 `.Nexus/2-Scheme/`
---
## 评审文档最少必须说明
- 读了哪些 fact / scheme / implement / review 文档
- 采用了哪种 review mode
- 静态发现
- fact 一致性审查结果
- 是否新增 / 修改测试
- 跑了哪些命令
- 结果如何
- 是否通过
- 若不通过，谁需要修什么
- 是否归档了实现文档
- 是否建议 Nexus 归档 scheme
- 是否需要用户手动确认 UI
